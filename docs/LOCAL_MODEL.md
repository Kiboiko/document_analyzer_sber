# Переход на локальную модель

Требование Д6: модель изолирована, провайдер берётся из конфига, локальный
вариант рабочий и к нему есть инструкция. Качество распознавания локальной
моделью не оценивается — важна работоспособность.

## Что где живёт

Все обращения к модели идут через один слой — `app/model/`. Больше нигде в
коде модель не вызывается, поэтому переезд на локальный вариант не требует
правок за пределами `.env`.

```
app/model/__init__.py       recognize(doc_type, image_bytes) -> ExtractResult
app/model/ocr.py            шаг 1: HTTP-сервис OCR -> текст
app/model/providers/cloud.py  шаг 2: Qwen через ilons API
app/model/providers/local.py  шаг 2: Ollama на своём железе
app/model/prompts/*.txt     промпты, по одному на тип документа
app/model/validate.py       нормализация и правила проверки полей
```

Разбор всегда двухшаговый:

1. **OCR** — HTTP-сервис организаторов (`OCR_SERVICE_URL`, за ним olmOCR)
   принимает файл как есть (PDF, PNG, JPEG, HEIC) и возвращает текст документа.
2. **LLM** — по промпту `prompts/<doc_type>.txt` извлекает из этого текста
   JSON с полями.

Локальный вариант заменяет **второй** шаг. OCR в обоих случаях один и тот же
выданный сервис, поэтому «переезд на собственную модель» означает: убрать
внешний API языковой модели (ilons).

## Переключение

Выбор провайдера — переменная `MODEL_PROVIDER`, значения `cloud` или `local`.
Читается в `app/model/get_provider()` при каждом разборе, константы в коде нет.

### 1. Поднять Ollama

Вариант А — контейнер из `docker-compose.yml`:

```bash
docker compose --profile ollama up -d
```

Вариант Б — Ollama, уже установленная на этой же машине. Контейнеры
приложения ходят к ней по имени `host.docker.internal` (Docker Desktop на
Windows и macOS). Так проверялось вживую, см. «Проверено вживую» ниже.

### 2. Загрузить модель

```bash
docker compose exec ollama ollama pull qwen2.5vl:3b
docker compose exec ollama ollama list      # убедиться, что модель на месте
```

Для варианта Б то же самое без `docker compose exec ollama`:
`ollama pull qwen2.5vl:3b`, затем `ollama list`.

Модель можно взять любую — важно, чтобы она умела следовать инструкции
«верни JSON». Имя задаётся переменной `LOCAL_VLM_MODEL` и должно в точности
совпадать с тем, что печатает `ollama list`.

### 3. Переписать `.env`

```
MODEL_PROVIDER=local
OLLAMA_HOST=http://ollama:11434       # вариант Б: http://host.docker.internal:11434
LOCAL_VLM_MODEL=qwen2.5vl:3b
```

`OCR_SERVICE_URL` и `OCR_CLIENT_TOKEN` не трогаем: OCR не меняется.

Остальные параметры, которые влияют на локальную модель:

| Переменная | Что делает | По умолчанию |
|---|---|---|
| `LLM_MAX_TOKENS` | потолок длины ответа; для Ollama уходит как `num_predict` | 2000 |
| `MODEL_TIMEOUT_S` | сколько ждать ответ модели; на CPU ставьте больше | 180 |

Пустое значение в `.env` (так выглядит файл сразу после
`cp .env.example .env`) считается «не задано», и берётся значение по умолчанию.

### 4. Пересоздать приложение и воркер

```bash
docker compose up -d --force-recreate app worker
```

Именно пересоздать, а не `docker compose restart`. Compose читает `.env`
только при создании контейнера, а `restart` запускает его со старым
окружением. Проверено: после `restart app worker` в контейнерах осталось
прежнее пустое `MODEL_PROVIDER`, то есть разбор продолжил бы идти через cloud.

Миграций и пересборки образа не нужно — поменялось только окружение.

### 5. Проверить

```bash
curl http://localhost:8000/health
# -> {"status":"ok", ..., "model_provider":"local"}
```

Затем загрузить документ через страницу соискателя и дождаться, пока он
выйдет из обработки (`done`, `flagged` или `error`). Каким провайдером он
разобран, видно в событии `parse_done` (см. ниже).

### Проверить локальный провайдер без приложения

```bash
MODEL_PROVIDER=local python tests/live_check.py passport_rf путь/к/файлу.jpg
```

Скрипт прогоняет файл по всей цепочке и печатает поля и статус проверки. OCR
в нём тоже настоящий (`OCR_SERVICE_URL`): он один и тот же в обоих вариантах. Сырой текст OCR и результат сохраняются в `data/live/`
(в `.gitignore`, там персональные данные).

## Проверено вживую — 2026-10-10

Локальный провайдер прошёл весь путь целиком: публичный API → очередь →
воркер → OCR → Ollama → валидация → статус документа.

**Окружение**

- Ollama 0.40.2 на той же машине (вариант Б), модель `qwen2.5vl:3b`
  (`ollama pull`, id `fb90415cde1e`).
- Стек из `docker-compose.yml`: postgres, keycloak, app, worker.
- В `.env`: `MODEL_PROVIDER=local`,
  `OLLAMA_HOST=http://host.docker.internal:11434`. Контейнеры пересозданы
  командой `docker compose up -d --force-recreate app worker`.
- OCR — сервис организаторов `https://ocr.ilons.ru`.

**Что сделано**

1. `GET /health` вернул `"model_provider":"local"`. В контейнерах app и
   worker `settings.model_provider == 'local'`.
2. Паспорт РФ из тестового пакета организаторов (`Case2_Package1`, JPEG,
   266 КБ) загружен от имени соискателя:
   `POST /api/applications` (`country=ru`), затем
   `POST /api/applications/{id}/documents` (`doc_type=passport_rf`).
3. Статус опрашивался раз в 2 с через `GET /api/applications/{id}/status`,
   пока документ не вышел из обработки.

**Результат**

Статус `flagged`. В событии `parse_done` записано `provider = local`.

| Шаг | Время |
|---|---|
| ответ API на загрузку | 0,5 с |
| от приёма до старта задачи в воркере | 0,8 с |
| OCR | 9,4 с |
| Ollama `/api/chat` | 31,7 с |
| от загрузки до финального статуса | 44,5 с |

| Поле | Что извлечено | Проверка |
|---|---|---|
| `series` | 4 цифры | ок |
| `number` | 7 цифр | ошибка: «Номер: ожидается 6 цифр, получено 7» |
| `full_name` | три слова кириллицей | ок |
| `birth_date` | `ДД.ММ.ГГГГ` | ок |
| `birth_place` | текст | ок |
| `issue_date` | `ДД.ММ.ГГГГ` | ок |
| `issued_by` | текст | ок |

Модель ошибку не выдумала. В тексте от OCR серия и номер склеились в одну
строку из 11 цифр, а 6-значного числа там нет вовсе. Модель разбила эту
строку на 4 + 7 цифр. Правило из `validate.py` поймало лишнюю цифру, и
документ ушёл оператору, а не в «готово». Так и задумано.

Тот же файл (тот же sha256) на этом стенде разбирался через `local` ещё
дважды, за полчаса до этого прогона. Результат тот же: `flagged` по той же
причине. Время задачи в воркере — 119 с и 103 с против 42 с в последнем
прогоне. Разброс даёт ответ Ollama: во втором прогоне он занял 92 с, в
последнем 32 с. OCR каждый раз отвечал примерно за 10 с.

**Что не проверялось**

- Вариант А: контейнер `ollama` из профиля compose. В этот раз работала
  Ollama на хосте.
- Другие типы документов и страны.
- Сбои Ollama вживую. Они покрыты тестами на моках,
  `tests/test_provider_errors.py`.
- Точность значений полей. С оригиналом их не сверяли: качество локальной
  модели по условиям кейса не оценивается.

После проверки `.env` возвращён в исходное состояние (провайдер `cloud`),
контейнеры пересозданы, `/health` снова показывает `"model_provider":"cloud"`.

## Как убедиться, что переключение реально работает

`/health` показывает только то, что написано в конфиге. Факт обращения именно
к локальной модели виден по `ExtractResult.provider`: модельный слой возвращает
туда имя сработавшего провайдера.

Договорённость с воркером (`worker.process_job`): это значение попадает в
`payload` события `parse_done`. Тогда подмену провайдера видно в истории
заявки, а не только в переменной окружения:

```bash
docker compose exec postgres psql -U app -d app -c \
  "select type, payload->>'provider' as provider, created_at
     from events where type = 'parse_done' order by created_at desc limit 5;"
```

## Если что-то не так

| Симптом | Причина | Что делать |
|---|---|---|
| `/health` после переключения показывает старый провайдер | контейнеры перезапущены через `restart`, `.env` не перечитан | `docker compose up -d --force-recreate app worker` |
| `Ollama /api/chat: ...Connection refused` | контейнер не поднят | `docker compose --profile ollama up -d` |
| `model "..." not found` | имя в `LOCAL_VLM_MODEL` не совпадает | сверить с `ollama list` |
| `в ответе модели нет JSON-объекта` | модель слишком мелкая, не держит формат | взять модель крупнее; `format: json` уже включён в запросе |
| `OCR недоступен` | сервис не отвечает или неверный `OCR_SERVICE_URL` | `curl $OCR_SERVICE_URL/health` должен вернуть `{"status":"ok",...}` |
| `OCR: сервис отклонил токен (HTTP 401)` | неверный или не заданный `OCR_CLIENT_TOKEN` | взять токен у организаторов |
| разбор очень долгий | модель считается на CPU | уменьшить `WORKER_CONCURRENCY`, взять модель меньше |
| `Ollama /api/chat: таймаут` | модель не успела ответить | увеличить `MODEL_TIMEOUT_S`, уменьшить `WORKER_CONCURRENCY` |
| `Ollama вернул пустой content` | модель ничего не ответила | повтор; если повторяется, модель не подходит |
| `Ollama обрезал ответ по лимиту токенов` | ответ не поместился в `num_predict` | увеличить `LLM_MAX_TOKENS` |
| `Ollama /api/chat: HTTP 5xx` | сервер Ollama упал или перегружен | смотреть `docker compose logs ollama` |
| `ответ не JSON` | перед Ollama стоит прокси, отдающий HTML | проверить `OLLAMA_HOST` |

Ошибка провайдера не роняет воркер: задача уходит в retry, документ получает
понятный статус, выдуманные поля в БД не попадают.

Все эти случаи одинаково обрабатываются у `cloud` и `local` (общий код в
`app/model/providers/__init__.py`), поэтому после переключения поведение при
сбоях не меняется. Обрезанный ответ считается ошибкой, даже если JSON в нём
разобрался: часть полей потеряна, а неполный документ хуже честной ошибки.
Проверяется `tests/test_provider_errors.py`.

## Сверка имени облачной модели

Имя модели в `LLM_MODEL` легко разъезжается с тем, что реально отдаёт шлюз.
Проверить:

```bash
curl -s -H "Authorization: Bearer $ILONS_API_KEY" \
  https://llm.ilons.ru/v1/models | python -m json.tool
```

То же самое делает `app.model.providers.cloud.list_models()`.
