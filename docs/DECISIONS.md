## 2. Разбор в два шага: OCR, затем LLM

**Что.** `recognize` сначала гонит картинку через olmOCR и получает текст,
и только потом отдаёт этот текст языковой модели для извлечения полей.

**Варианты.**
- Одна VLM: сразу картинка → JSON с полями.
- Два шага: OCR → текст → LLM → JSON.

**Почему так.** olmOCR — специализированная модель именно под чтение
документов, она читает мелкий шрифт и повёрнутые фото лучше универсальной VLM.
Главное, это условие «переезда на собственную модель» (Д6): OCR уже self-hosted,
поэтому для полного on-prem достаточно заменить второй шаг локальной моделью,
не трогая первый. Одношаговая VLM потребовала бы менять весь разбор целиком.

**Риск.** Ошибка OCR не исправляется на втором шаге: если текст прочитан
неверно, LLM извлечёт неверное поле. Поэтому `raw_text` сохраняется, оператор
видит оригинал рядом с полями и может исправить значение. Второй риск —
обрезанный ответ: страница, прочитанная не до конца, дала бы «разобранный»
документ без части полей. Обрезка (`finish_reason=length`) на обоих шагах
считается ошибкой и уходит в retry, а не принимается как результат.

## 3. Провайдер LLM выбирается переменной окружения

**Что.** `MODEL_PROVIDER=cloud|local` читается при каждом разборе
(`app/model/get_provider()`). Оба провайдера (`providers/cloud.py` для ilons
и `providers/local.py` для Ollama) реализуют одну функцию
`complete_json(prompt, text) -> LLMResult`, а разбор ответа и обработка сбоев
вынесены в общий код `providers/__init__.py`. Вызовы модели есть только в
`app/model/`.

**Варианты.**
- Флаг в коде или отдельная сборка под каждый вариант.
- Фабрика по переменной окружения, у каждого провайдера свои проверки ответа.
- Фабрика по переменной окружения, общий контракт и общая обработка сбоев.

**Почему так.** Требование Д6 — сменить провайдера без правки кода: на защите
это одна строка в `.env` и `docker compose restart`. Общая обработка сбоев
нужна, потому что два провайдера иначе расходятся: пока проверки были у каждого
свои, у cloud обрезанный ответ считался ошибкой, а у local обрезанный, но
валидный JSON молча принимался. Теперь таймаут, 5xx, не-JSON в теле, пустой
`content` и обрезка по лимиту дают одинаковую `ProviderError` на обоих.

**Риск.** API у ilons и Ollama разные (`/v1/chat/completions` против
`/api/chat`), различия спрятаны внутри модулей провайдеров; третий провайдер
потребует сверить формат ответа. Кроме того, формат ответа живого olmOCR и
ilons проверен только на моках — до первого прогона на настоящих серверах это
точечная правка разбора, а не гарантия.

## 4. Нормализация и валидация — в коде, а не в промпте

**Что.** Промпт говорит только, что извлечь и в каком виде. Приведение значений
(даты к ДД.ММ.ГГГГ, СНИЛС к `XXX-XXX-XXX YY`, серия и номер паспорта к цифрам,
серия и номер слитно — к раздельным) и все проверки раздела 3 ТЗ живут в
`app/model/validate.py`. Просрочка документа даёт `flagged` и не блокирует
приём; в `error` документ уходит только если не собрался минимум полей.

**Варианты.**
- Просить модель сразу валидировать и возвращать признак корректности.
- Валидация отдельным детерминированным кодом.

**Почему так.** Проверка бизнес-результата должна быть воспроизводимой: на
одних и тех же данных ответ обязан быть одинаковым, его нужно уметь объяснить
оператору и проверить тестом. Модель может «посчитать» просроченный документ
действительным. Правила тестируются без сети: `tests/test_validate.py`.
Нормализация нужна не для красоты: без неё хорошие документы получали ложные
замечания. Например, `JOSÉ MÜLLER` в удостоверении ЕС помечался как «не
латиница», а дата `01 JAN 1990` не разбиралась.

**Риск.** Правила продублированы относительно того, что модель и так понимает;
при изменении требований править нужно в двух местах — промпт и `validate.py`.
Для этого `tests/test_prompts.py` сверяет ключи в промптах с `enums.py`.
`flagged` смешивает разные поводы (просрочка, формат, расхождение), поэтому
причина всегда пишется текстом в `Document.error_reason` и
`Field.validation_msg`, а не выводится из статуса.

## 5. Сопоставление ФИО и дат между документами заявки

**Что.** `services/crosscheck.py` сверяет ФИО и дату рождения по всем
документам одной заявки. ФИО нормализуются (регистр, ё/е, дефисы),
приводятся к одному алфавиту транслитерацией и сравниваются нечётко: слова
сопоставляются один к одному (перебор перестановок, в ФИО не больше четырёх
слов), порог совпадения 0,82. Результат — одна запись `CrossCheck` на пару
(заявка, вид сверки); событие `document_flagged` пишется один раз, когда
расхождение появилось, а не на каждый повторный прогон.

**Варианты.**
- Точное сравнение строк.
- Нечёткое сравнение всей строки целиком.
- Нечёткое сравнение по словам, каждое слово ищет лучшую пару.
- Нечёткое сравнение по словам с сопоставлением один к одному.

**Почему так.** Точное сравнение не годится: OCR ошибается на одну букву, в
паспорте РФ ФИО кириллицей, а в удостоверении ЕС латиницей, и в одном из
документов может не быть отчества. Сравнение строки целиком наказывает за
отсутствующее отчество. Жадный поиск лучшей пары по словам оказался неверным:
«Иванов Иван» и «Сидоров Иван» получали 90% сходства, потому что фамилия
«Иванов» находила себе пару в имени «Иван». Сопоставление один к одному
(«Иванов Иван» против «Сидоров Иван» даёт 73%) это исправило. Дальше всё
решает человек: расхождение — это замечание в карточке оператора, а не
отказ в приёме.

**Риск.** Порог 0,82 подобран примерно на десятке искусственных пар, а не
на реальных документах. Фамилии, различающиеся только окончанием, проходят как
совпадение: «Смирнов Иван» и «Смирнова Иван» дают 97%, «Петров Пётр» и
«Петрова Пётр» 96%. Это та же ошибка OCR по последней букве, которую мы и не
хотим считать расхождением, но заодно сюда попадут родственники и супруги.
Чтобы их различать, нужно сравнивать род окончания отдельно; сейчас не
делаем. Транслитерация упрощённая,
не по ГОСТ: «Шмидт» и «Schmidt» сходятся (84%), но у самой границы порога.
После настройки на открытом наборе порог стоит перепроверить.

## 6. Доступ соискателя — по невычисляемому токену

**Что.** Заявка открывается по ссылке `/a/{applicant_token}`, где токен —
UUID4. Ни логина, ни пароля у соискателя нет. Проверка — на сервере, на каждом
запросе, через `secrets.compare_digest`.

**Варианты.**
- Регистрация соискателя (логин/пароль или SMS).
- Доступ по id заявки.
- Доступ по отдельному невычисляемому токену.

**Почему так.** ТЗ требует публичную страницу без входа. Доступ по id заявки
позволил бы перебирать чужие документы, а регистрация — лишний барьер для
человека, который пришёл с телефона загрузить три фотографии.

**Риск.** Кто получил ссылку — получил доступ к PII заявки. Поэтому токен
отдельный от id, не выводится из него и нигде не показывается рядом с
персональными данными; на несовпадение токена и на отсутствие заявки ответ
одинаковый (404), чтобы нельзя было узнать, какие заявки существуют. Оригиналы
файлов соискателю не отдаются совсем: их выдаёт только маршрут оператора,
который проверяет цепочку заявка → документ → файл.
