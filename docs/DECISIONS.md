# Принятые решения

Формат: что / какие были варианты / почему так / какой риск. Нужно 3–6 решений.

## 1. Очередь в Postgres вместо брокера
**Что.** Задачи разбора — таблица `jobs` в той же Postgres, выборка через
`SELECT ... FOR UPDATE SKIP LOCKED`, а не Redis/RabbitMQ/Celery.

**Варианты.**
- Внешний брокер: надёжнее под нагрузкой, но +1 сервис в compose и +1 точка отказа.
- Очередь таблицей в Postgres: без доп. инфраструктуры, транзакционно
  согласована с данными заявки.

**Почему так.** Масштаб кейса не требует брокера, а транзакционная
согласованность решает главную задачу: `Job`, `Document` и `Field` правятся
в одной БД и одной транзакцией, поэтому после рестарта не бывает состояния
«задача выполнена, а поля не записаны» (ТЗ 4, Д4).

**Риск.** `SKIP LOCKED` не даёт из коробки приоритетов и отложенных задач.
Для объёма кейса это не нужно; при росте нагрузки пришлось бы брать брокер.

## 2. Воркер отдельным процессом

**Что.** `python -m app.worker` — отдельный процесс, а не фоновая задача
внутри FastAPI (`BackgroundTasks` / `asyncio.create_task` в веб-процессе).

**Варианты.**
- Фон в процессе API: проще, но падает и рестартует вместе с API и делит
  с обработкой запросов один event loop.
- Отдельный процесс: независимый жизненный цикл, параллельность регулируется
  `WORKER_CONCURRENCY`.

**Почему так.** Приём обязан быть мгновенным и не блокироваться разбором
(ТЗ 6). Отдельный процесс даёт это по построению, а реапер на старте
возвращает в `pending` задачи, которые кто-то взял и не довёл — поэтому
перезапуск воркера не теряет работу.

**Риск.** Два процесса — сложнее деплой и чтение логов. Снимается тем, что
оба поднимаются одним `docker-compose.yml`, а `services/queue.py` остаётся
единственным контрактом между приёмом и воркером.

## 3. Разбор в два шага: OCR, затем LLM

**Что.** `recognize` сначала гонит картинку через olmOCR и получает текст,
и только потом отдаёт этот текст языковой модели для извлечения полей.

**Варианты.**
- Одна VLM: сразу картинка → JSON с полями.
- Два шага: OCR → текст → LLM → JSON.

**Почему так.** Выданный нам olmOCR — специализированная модель именно под
чтение документов, она читает мелкий шрифт и повёрнутые фото лучше, чем
универсальная VLM. А главное, это условие «переезда на собственную модель»
(Д6): OCR уже self-hosted, поэтому для полного on-prem достаточно заменить
второй шаг локальной моделью, не трогая первый. Одношаговая VLM потребовала бы
менять весь разбор целиком.

**Риск.** Ошибка OCR не исправляется на втором шаге: если текст прочитан
неверно, LLM извлечёт неверное поле. Смягчаем тем, что `raw_text` сохраняется
и оператор видит оригинал рядом с полями, а поля правятся вручную.

## 4. Провайдер модели выбирается переменной окружения

**Что.** `MODEL_PROVIDER=cloud|local` читается при каждом разборе
(`app/model/get_provider()`), оба провайдера реализуют одну функцию
`complete_json(prompt, text) -> LLMResult`. Вызовы модели есть только в
`app/model/`.

**Варианты.**
- Флаг в коде или отдельная сборка под каждый вариант.
- Фабрика по переменной окружения.

**Почему так.** Требование Д6 — сменить провайдера без правки кода. На защите
это одна строка в `.env` и `docker compose restart`, а не пересборка.
Изоляция в одном слое заодно означает, что ни роутеры, ни воркер не знают,
какая модель работает.

**Риск.** Контракт провайдера приходится держать одинаковым, хотя API у ilons
и Ollama разные (`/v1/chat/completions` против `/api/chat`). Различия спрятаны
внутри модулей провайдеров, но добавление третьего провайдера потребует снова
сверить формат ответа.

## 5. Нормализация и валидация — в коде, а не в промпте

**Что.** Промпт говорит только, что извлечь и в каком виде. Приведение значений
(даты к ДД.ММ.ГГГГ, СНИЛС к `XXX-XXX-XXX YY`, серия к цифрам) и все проверки
раздела 3 ТЗ живут в `app/model/validate.py`.

**Варианты.**
- Просить модель сразу валидировать и возвращать признак корректности.
- Валидация отдельным детерминированным кодом.

**Почему так.** Проверка бизнес-результата должна быть воспроизводимой: на
одних и тех же данных ответ обязан быть одинаковым, его нужно уметь объяснить
оператору и проверить тестом. Модель на это не годится — она может «посчитать»
просроченный документ действительным. Плюс правила легко тестируются без сети:
`tests/test_validate.py` проходит 42 проверки на всех 8 типах.

**Риск.** Правила продублированы относительно того, что модель и так понимает;
при изменении требований править нужно в двух местах — промпт и `validate.py`.

## 6. Просрочка — это `flagged`, а не `error`

**Что.** Документ с истёкшим сроком принимается, разбирается и помечается
`flagged` с замечанием. В `error` документ уходит только если не собрался
минимальный набор полей (`MIN_FIELDS`).

**Варианты.**
- Отклонять просроченные на приёме.
- Принимать и помечать.

**Почему так.** Прямое требование ТЗ (раздел 3). По сути верно: просроченный
паспорт — это факт о соискателе, который кадровик должен увидеть, а не повод
потерять загруженный файл. Решение, что делать с просрочкой, принимает человек.

**Риск.** `flagged` смешивает разные поводы (просрочка, нарушение формата,
расхождение между документами). Поэтому причина всегда пишется текстом в
`Document.error_reason` и в `Field.validation_msg`, а не выводится из статуса.

## 7. Доступ соискателя — по невычисляемому токену

**Что.** Заявка открывается по ссылке `/a/{applicant_token}`, где токен —
UUID4. Ни логина, ни пароля у соискателя нет. Проверка — на сервере, на каждом
запросе, через `secrets.compare_digest`.

**Варианты.**
- Регистрация соискателя (логин/пароль или SMS).
- Доступ по id заявки.
- Доступ по отдельному невычисляемому токену.

**Почему так.** ТЗ требует публичную страницу без входа. Доступ по id заявки
позволил бы перебирать чужие документы, а регистрация — лишний барьер для
человека, который пришёл с телефона загрузить три фотографии.

**Риск.** Кто получил ссылку — получил доступ к PII заявки. Поэтому токен
отдельный от id, не выводится из него и нигде не показывается рядом с
персональными данными; на несовпадение токена и на отсутствие заявки ответ
одинаковый (404), чтобы нельзя было узнать, какие заявки существуют.
