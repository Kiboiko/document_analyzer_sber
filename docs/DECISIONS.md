# Принятые решения

Формат: что / какие были варианты / почему так / какой риск. Нужно 3–6 решений.

## 1. Очередь в Postgres вместо брокера
Что: задачи разбора — таблица `jobs` в той же Postgres, выборка через
`SELECT ... FOR UPDATE SKIP LOCKED`, а не Redis/RabbitMQ/Celery.
Варианты: внешний брокер (надёжнее при высокой нагрузке, но +1 сервис в
compose, +1 точка отказа); Postgres-очередь (без доп. инфры, транзакционно
согласована с данными заявки).
Почему: масштаб кейса не требует отдельного брокера, а транзакционная
согласованность (Job и Document/Field правятся в одной БД) упрощает
восстановление после рестарта (TZ 4, Д4).
Риск: SKIP LOCKED не даёт приоритетов/задержанных задач из коробки; при
росте нагрузки потребуется отдельный брокер — но для объёма кейса это не
критично.

## 2. Воркер отдельным процессом
Что: `python -m app.worker` — отдельный процесс, не background-задача внутри
FastAPI (`BackgroundTasks`/`asyncio.create_task` в веб-процессе).
Варианты: фон в процессе API (проще, но падает/рестартует вместе с API,
делит CPU/GIL с обработкой запросов); отдельный процесс (переживает
перезапуск API, масштабируется независимо asyncio-семафором
`WORKER_CONCURRENCY`).
Почему: приём обязан быть мгновенным и не блокироваться разбором (TZ 6);
отдельный процесс даёт независимый жизненный цикл и реапер зависших задач
на старте.
Риск: два процесса — сложнее деплой и логи; решаем общим `docker-compose.yml`
и единым `services/queue.py` как контрактом между приёмом и воркером.
